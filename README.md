# 桌面 AI 助手

按《[PRODUCT\_DESIGN.md](./PRODUCT_DESIGN.md)》和《[docs/TECHNICAL\_PLAN.md](./docs/TECHNICAL_PLAN.md)》  
实现的 Windows 桌面 AI 助手。

**进度：阶段 A、B、C、D 全部完成；阶段 E 进行中。**  
阶段 D 依次做了：本地文件读取与路径权限、截屏、把文件和截图接进对话上下文、  
键鼠模拟与可控自动化任务。阶段 E 的第一步是**让模型自己请求附件**（工具调用）。

```text
配置模型 → 流式聊天 → 会话本地保存 → 关掉 → 再打开 → 历史还在
```

这条闭环在两种运行模式下都是通的，区别只在「谁在回答、东西存在哪」：

|         | 浏览器模式（`npm run dev`） | 桌面模式（`npm run dev:desktop`）        |
| ------- | -------------------- | ---------------------------------- |
| 模型回答    | 本地离线实现，不联网           | **Rust 侧发起真实请求**（OpenAI 兼容）        |
| 会话数据    | 浏览器 localStorage     | **SQLite**，应用数据目录                  |
| API Key | 只留内存，刷新即失效           | **Windows 凭据管理器**加密保管              |
| 网络出口    | 无                    | 只在 Rust 侧，WebView 无外网权限            |
| 关闭窗口    | 关掉标签页就是关掉            | 默认**缩到系统托盘**，可关                    |
| 系统托盘    | 没有（界面如实说明）           | 有：显示 / 隐藏 / 退出                     |
| 完成通知    | 用浏览器通知（需授权）          | **系统通知**，窗口在前台时不打扰                 |
| 开机自启    | 没有（界面如实说明）           | 有，状态读自系统                           |
| 全局快捷键   | 没有（界面如实说明）           | 有，默认不设                             |
| 本地文件    | 没有（界面如实说明）           | **授权目录 + 相对路径**，默认未授权；可选中文件作为对话附件  |
| 截屏      | 没有（界面如实说明）           | **默认关闭**，截图不落盘；当前预览图可作为对话附件        |
| 自动化     | 没有（界面如实说明）           | **默认关闭**，四种有限动作，每次执行前预览 + 确认，可随时停止 |
| 工具调用    | 没有（界面如实说明）           | 模型可主动请求读文件 / 截屏，**每次都要你点头**        |
| 用途      | 开发、跑测试、看界面           | 日常使用                               |

浏览器模式**至今**仍然是离线实现，这不是没做完 —— 见下面「为什么浏览器模式不接真模型」。

## 快速开始

需要 Node.js 20+（用到 22）与 Rust 1.90+（用到 1.99）。

```bash
npm install

# 浏览器模式：打开 http://localhost:5173
npm run dev

# 桌面模式：启动 Tauri 开发窗口
npm run dev:desktop

# 打桌面产物（生成 exe，不打安装包）
npx tauri build --no-bundle
```

## 验收前先分清：环境限制 vs 项目问题

这个项目被外部环境验收过一次，报了两个错，结论是「无法严谨宣布验收通过」。  
那两个错**都不是项目的问题**，是执行环境的限制。为了不再重复这种拉扯，有了 `npm run doctor`。

### 两个典型症状

| 报错                                                                                           | 真实原因                                                                                                           | 怎么确认                                                                |
| -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `Could not load @tailwindcss/oxide-win32-x64-msvc`<br />`stream did not contain valid UTF-8` | **环境把二进制当文本读**。`.node` 是 Windows PE 二进制，正常 Node 用 `process.dlopen` 加载它，永远不会去解码成 UTF-8。会报这个错，说明有东西拦了文件读取并按文本解码。 | `npm run doctor` 会校验 PE 文件头（`MZ`）并实际 import 一次。文件头正常 + 加载成功 = 环境问题。 |
| `Error: spawn EPERM`<br />（`node --test` / Vitest 起不来）                                       | **环境禁止创建子进程**。`node --test` 每个测试文件起一个子进程，Vitest 起 worker 进程，都需要这个能力。                                           | `npm run doctor` 会真的 spawn 一个 `node -e` 试一次。                        |

### 怎么用

```bash
npm run doctor     # 先看这一行结论
npm run test:all   # 环境没问题再跑
```

`doctor` 失败时会直接写清「这通常意味着什么」。比如子进程那条会说：  
*这是执行环境的限制，不是项目问题 —— 请在普通终端里跑测试，或给沙箱放开进程创建权限。*

它检查 6 项：Node 版本、依赖目录、Tailwind 原生模块（含 PE 头校验与真实加载）、  
子进程创建能力、Rust 工具链、前端构建产物（仅提示）。

### 给验收方的建议

在**普通 Windows 终端**（PowerShell 或 cmd，不在任何 AI 沙箱内）执行：

```powershell
npm install
npm run test:all
npx tauri build --no-bundle
```

重点确认三件事：`doctor` 是否 6 项全绿、前端构建是否**没有 chunk 警告**、  
契约/单元/E2E 是否都能起来。

Rust 侧的凭据测试会**真的读写 Windows 凭据管理器**（用独立的条目名，跑完即删）。

端到端用 `playwright-core` + 本机 Chrome，不下载浏览器内核；可用 `CHROME_PATH` 指定。

## 托盘与窗口（阶段 C 第一步）

「关掉窗口但程序还在跑」是桌面助手的常见设计，也是最容易被误解的设计 ——  
用户点完叉发现进程还在，第一反应是「这软件关不掉」。所以这一步的重点不是托盘本身，  
而是**不让用户被困住**：

- 关闭窗口默认缩到托盘，但设置页有一个明确的开关可以关掉；
- 托盘菜单同时有「显示主窗口」和「退出」—— 少任何一个，用户都会被困住；
- 托盘可用性是 **Rust 运行时判断**的，不是前端写死的：托盘创建失败时  
  `decide_close_action` 会退回「关闭即退出」，而不是把窗口藏起来又找不到入口。

关闭行为的判定被抽成纯函数（`src-tauri/src/window.rs`），三个输入两个结果，  
每个分支都有用例 —— 因为这个逻辑写错时的表现是「点了关闭但窗口没关」，  
没有任何报错，只会让用户觉得软件坏了。

**托盘没有引入任何 Tauri 权限。** 它走的是 Tauri 核心的 tray API  
（`Cargo.toml` 里开 `tray-icon` feature），完全在 Rust 侧建立和响应；  
前端只多拿到 4 条自己的窄命令，`capabilities/default.json` 里仍然只有 `core:default`。  
这一点有契约测试盯着（`新增原生能力没有顺带放开任何 Tauri 权限`）。

## 系统通知（阶段 C 第二步）

**这一项引入了第一个 Tauri 插件**（`tauri-plugin-notification`），  
但前端仍然只多拿到两条自己的窄命令，`capabilities/default.json` 里**依然只有 `core:default`**。

### 为什么插件只在 Rust 侧用

插件自带一套前端 JS API，用起来更省事。之所以不用，是因为这一项最关键的判断在 Rust 侧：

```
回复完成 → 前端只说「有结果了」→ Rust 判断：窗口在前台吗？
                                     ├── 是 → 跳过（用户正看着呢）
                                     └── 否 → 发通知
```

前端**拿不到窗口的可见性与焦点状态**。要自己判断，就得再加一条查询命令，  
而且策略被拆到两处，迟早分叉。现在策略只有一处（`src-tauri/src/notify.rs`）。

顺带的好处是权限：前端没碰插件，就不需要在 capabilities 里放开插件权限。  
有契约测试盯着这条（`插件不在前端开放，仍然只走自己的窄命令`）。

### 什么时候会响

| 情况              | 发不发       | 为什么                 |
| --------------- | --------- | ------------------- |
| 窗口缩到托盘，回复完成     | **发**     | 通知存在的全部理由           |
| 窗口可见但被别的程序挡住    | **发**     | 用户看不到回复             |
| 窗口可见且聚焦         | 不发        | 用户正看着流式输出，再弹一条是纯打扰  |
| 用户点了「停止」        | 不发        | 他就在屏幕前，而且是他自己按的     |
| 回复出错            | **发**     | 否则切走之后消息会悄无声息地失败    |
| 点了设置页的「发一条测试通知」 | **发**（强制） | 用户明确要求看到它，此时窗口必然在前台 |

打扰判定被抽成纯函数 `should_notify(visible, focused)`，四种组合的**真值表**都有用例 ——  
因为它判反了不会报错，只会让用户莫名收到通知，或者切走了却什么都没收到。

### 桌面端没有授权流程，这是刻意的

在 Windows 上，`permission_state()` 与 `request_permission()` **恒返回 `Granted`**  
（插件自己的文档就这么写）。照着 Web 的思路写一套「查询 → 请求 → 再查询」的流程，  
在这里就是死代码，还会让读代码的人以为真有一个授权步骤。

真正控制通知开关的地方是 Windows 的「设置 → 系统 → 通知」，逐应用生效，  
应用自己查不到也改不了。所以界面上如实这样说，而不是给一个点了没用的按钮。

浏览器模式则相反：授权是真实的，而且**只在用户明确点按钮时才发起申请** ——  
浏览器要求授权提示由用户手势触发，在「回复完成」这种后台时机去申请，既会被静默拒绝，又会平白打扰一次。

## 开机自启（阶段 C 第三步）

用 `tauri-plugin-autostart`。这是第三个插件，同样**只在 Rust 侧使用**，  
前端只多拿到两条窄命令，`capabilities` 里依然只有 `core:default`。

### 状态存在系统里，不存我们的数据库

自启状态**刻意不写进 settings 表**。系统才是权威：注册表里那条记录随时可能被用户在  
「任务管理器 → 启动应用」里关掉。我们存一份副本只会和系统对不上，  
然后界面显示一个错的开关。所以每次都去问 `autolaunch().is_enabled()`。

顺带一个好处：`is_enabled()` 连「用户在任务管理器里禁用了」都能反映出来，  
这个判断自己实现要读两处注册表。

### 两个 Windows 上的坑，都做成了界面文案

1. **注册的是 exe 的绝对路径。** 把 exe 挪走，自启就失效了，  
   但 `is_enabled()` 仍然返回 `true` —— 它只检查那条记录在不在，不比对路径。  
   所以设置页把**将要写入的路径**显示出来，并提示「重新开关一次可以刷新路径」。  
   开发模式下尤其要注意：跑 `tauri dev` 时注册的是 `target/debug` 下的那个 exe。
2. **以管理员身份运行可能写进 HKLM。** 底层库的策略是「先试 HKLM，权限不够再退到 HKCU」，  
   所以提权运行一次就会变成对全机器生效，而不是只对当前用户。

### 重置本地数据不会关掉它

自启是系统设置，不在「本地数据」范围内。重置对话框里写明了这一点，  
并有单元测试断言「重置后系统里仍然是开着的」—— 避免有人顺手把系统状态也清了。

## 全局快捷键（阶段 C 第四步）

用 `tauri-plugin-global-shortcut`。第四个插件，同样**只在 Rust 侧使用**，  
`capabilities` 里依然只有 `core:default`。

### 难点不在注册，在「注册失败」

全局快捷键抢的是**全系统唯一**的组合键。用户想设 `Ctrl+Shift+Space`，  
它很可能已经被输入法或截图工具占了。那时注册会失败 ——  
而**用户看到的只是「按了没反应」**，他不会想到是键被占了，只会觉得软件坏了。

所以做了三件事：

1. **注册失败时直接说「可能被别的程序占用」**，并给出下一步（换一个试试），  
   而不是把 OS 层面的原始错误抛给用户；
2. **先注册新的，成功了再撤旧的。** 直觉写法是反过来，但那样一旦新键注册失败，  
   用户会掉进「一个快捷键都不生效、界面却还显示旧的那个」的状态 ——  
   这类失败路径上的状态一致性是这个功能里最值得较真的地方；
3. **拒绝没有修饰键的组合。** 单独注册一个 `K`，用户在任何程序里打这个字母都会被截走。  
   前端录制时拦一道，Rust 侧再校验一道（前端不是可信边界）。

### 拒绝「全是修饰键」这种写法

`Ctrl+Alt` 语法上是成立的，但它没有任何实际按键，注册出去没有意义。  
这个漏洞是**单元测试抓出来的** —— 我原本的校验只检查了「最后一段非空」，  
`Ctrl+Alt` 的 `Alt` 非空就过了。现在会明确拒绝并说明缺一个实际按键。

### 「设了但没生效」必须能看见

同一个组合键可能被占用，所以设置页把两件事**分开显示**：  
你设的是哪个键、它现在到底有没有生效。注册状态来自运行期查询，不是乐观假设。


### 默认不设，这一点和别的设置相反

窗口和通知都默认开着，全局快捷键默认**空**。理由：它占用的是全系统唯一的键位，  
开着一个就等于从别的程序手里拿走一个键。影响超出本应用范围的事，  
必须由用户主动选择。

### 重置数据会连带撤销系统里的注册

「重置本地数据」清的是我们数据库里的设置，但那个热键**已经注册到系统里了**。  
只清库不撤销的话，用户会看到「设置里明明是空的，可那个键还在起作用」。  
所以 `reset_all_data` 会顺手把快捷键注销、把关闭行为的缓存恢复成默认值。  
有契约测试盯着这条（`重置本地数据要顺手撤销系统层面的副作用`）。

## 本地文件读取与路径权限（阶段 D 第一步）

技术方案第 6 节第 3 项写的是「本地文件读取**和路径权限**」—— 路径权限是需求本身的一部分，  
不是可选的加固。第 8 节还要求这些能力「**在权限、确认和日志机制完善后**」再加进来，  
所以这一步的重点不是「怎么读文件」，而是**怎么保证只读到授权的范围里**，  
以及怎么把这件事对用户说清楚。

### 三道输入 + 四道防线

前端能碰到的只有两条文件命令，参数都是**相对授权目录的路径**：

```
read_authorized_file(relative_path)     ← 不是绝对路径
list_authorized_directory(relative_dir)
```

四道检查依次是：

|   | 防线            | 挡住什么                             |
| - | ------------- | -------------------------------- |
| 1 | 前端只表达相对路径     | 让前端**连说「读 D:\别处」的能力都没有**         |
| 2 | 逐段检查，`..` 直接拒 | 上跳逃逸；也拒绝了「绕一圈还在范围内」的写法——简单规则更难写错 |
| 3 | 路径上任一段是符号链接就拒 | 目录里放个链接指向外面                      |
| 4 | 规范化后比对前缀      | 兜底                               |

全部集中在 `file_access::resolve_within_root` 一处，有独立用例覆盖每一类绕过手法。

### 第 3 道防线是「假设被测试推翻」之后才加的

最初只写了 1、2、4，注释里断言「只有 canonicalize 之后比对前缀，才能挡住符号链接指向目录外」。  
**这句话在 Windows 上不成立。**&#x5355;元测试实测：`std::fs::canonicalize` 对「最后一段是符号链接」  
的情况原样返回了链接自身的路径，于是「链接指向目录外」被判成了安全。

修法不是去研究 canonicalize 在什么条件下解析（那种正确性依赖平台行为细节，随时可能变），  
而是干脆**不让路径经过任何符号链接** —— 规则简单、跨平台一致，对用户也解释得清楚。

### 顺带修掉的一个真 bug：截断切坏了 UTF-8

大文件按字节截断，可能刚好切在一个多字节字符中间，于是 `String::from_utf8` 失败，  
一个完全正常的 UTF-8 文本被报成「这不是文本」。

现在会检查 `valid_up_to`：**只在确实发生了截断**时接受那个合法前缀  
（没截断却解不出 UTF-8，那它真的不是文本）。加了一段「读 300 KB 中文文本」的用例盯着。

### 权限、确认、日志分别落在哪

| 要求     | 落点                                             |
| ------ | ---------------------------------------------- |
| **权限** | 用户显式授权**一个**目录，存规范化后的绝对路径；没授权就一个字节也读不到。默认**空** |
| **确认** | 授权分两步：选/填路径 → 点「授权读取」。中间那一步是给用户看清范围的机会         |
| **日志** | 每次成功读取都记一条，界面上「最近读取」列表能看到它刚读了什么                |

「最近读取」**只在内存里，不落盘** —— 阅读记录落到磁盘就变成了对用户阅读史的长期保存，  
那是另一件事，不该顺手做掉。

### 顺带说明的几件事

- **授权整个磁盘会提醒但不阻断。** 用户的机器他自己做主，但「把整个 C 盘授权出去」  
  多半是误操作，值得说一句。
- **只认 UTF-8。** 中文 Windows 上一些旧 .txt 是 GBK，会被判为「不是文本」而不是给出乱码。  
  没做编码探测是个取舍，见「已知缺口」。
- **撤销只影响我们这一侧。** 撤销后立刻读不到任何文件；已经进过对话的内容不会因此消失。

## 截屏与高风险能力的通用门禁（阶段 D 第二步）

用 `xcap` 抓主屏，编码成 PNG 的 data URL 回给设置页前端预览。

这一项的意义不只是「能截图」，而是**把高风险能力的处理模式定下来** ——  
技术方案第 6 节把截屏和键鼠模拟并列要求「明确的设置开关、失败提示和权限说明，  
默认关闭高风险自动化能力」，所以两者应当走同一套。这套模式写在  
`src-tauri/src/permissions.rs`，键鼠模拟照着抄。

当前阶段截图只在设置页手动预览，**不会自动附加到聊天请求或发给模型**；后续接入多模态请求时需另行增加明确的发送确认。

### 模式：四件事

1. **默认关闭。** 不是「默认开着但提示一下」，是真的关着、调不动。
2. **门开在 Rust 侧。** 见下。
3. **失败说人话。** 拒绝时要说清三件事：这是什么能力、现在为什么不能用、去哪里开。
4. **每次使用都留痕。** 日志记一条，界面上能看到最近一次用了什么。

### 门必须设在 Rust 侧 —— 这是最容易做错的一步

前端那个开关表达的是**用户意图**，不是**权限**。命令是可以被直接调用的：  
打开 devtools 手动 `invoke` 就行，完全不需要走我们写的任何界面逻辑。

所以「开关关着就不许用」这个判断发生在 `take_screenshot` 命令的第一行  
（`permissions::ensure_enabled`）。界面上把按钮禁掉、甚至整张卡片不渲染，  
都只是体验，不是约束。有契约测试盯着这条。

### 截图不落盘

**这条命令不写任何文件。** 图片编码成 data URL 直接回给前端，由前端放在内存里用。

不落盘的理由有两条：一是截图里可能有用户自己都没意识到的东西  
（别的窗口、通知弹窗、密码框），二是临时文件在哪儿、什么时候删都要额外管。  
不落盘就都不存在。

「只返回临时引用」在这里的含义是：**没有路径、没有临时文件**，  
只有一个用完就会被丢掉的字符串。关掉开关时，前端连上一次的画面也一并丢掉。  
有契约测试断言这个模块里不出现写文件操作。

### 默认关闭 + 失败方向选「关」

数据库里读这个开关时只认明确的 `"true"`：值写坏了、键被删了、  
字段漏了，一律回到「关闭」。高风险能力的开关，出问题时的方向必须是关。

### 实际能力与实测

- 抓的是**主屏的整块画面**，不是某个窗口、不是某块区域
- 检测到多块屏时会**如实告诉用户只截了主屏**，而不是默默只给一块
- 编码后超过 32 MB 会被拒绝（实测 2560×1440 桌面约 2 MB，离上限很远）
- Rust 侧有一条**真去抓一张**的用例，开发机上实测通过：  
  `2560×1440`、1 块屏、PNG 约 2 MB。无头环境里枚举不到屏幕会如实跳过并打印原因，  
  但除了「没有屏幕」之外的失败一律当真失败 —— 否则 xcap 哪天坏了也会被当成环境问题放过去

## 把文件和截图接进对话（阶段 D 第三步）

前两步做完，能力是「能用」但不是「有用」——文件读出来了只能自己看一眼，  
截图抓完也只是挂在设置页里。这一步把它们变成对话的一部分。

### 两种附件，其实是两种东西

|    | 走什么格式                             | 谁收得下      |
| -- | --------------------------------- | --------- |
| 文件 | 拼进 prompt 的**文本**部分               | 任何模型      |
| 截图 | OpenAI 的 `image_url` **多模态** part | 只有支持视觉的模型 |

所以它们在类型上就是两个形态（`ChatAttachment` 是联合类型/枚举，不是一个结构加个 flag），  
而不是靠调用方记得「图片那个字段是空的」。

### 请求组装：没有附件时一个字节都不变

`content` 只在**有附件时**才从字符串变成数组。这样改动的面最小 ——  
绝大多数请求走的还是原来的路径，原有测试也继续有意义。  
有一条用例专门盯着这件事（`a_turn_without_attachments_still_sends_a_plain_string`）。

**附件放在用户的话之前。** 长文件接在问题后面的话，模型读完问题还要再啃一大段  
才轮到回答；把附件放前面、问题放最后，模型最后读到的才是它要回答的东西。  
这是刻意的顺序，有测试断言。

### 附件内容跟着消息一起入库

这是这一步最需要解释的一个决定。`0002_attachments.sql` 把附件**存在消息里**，  
而不是只留一个「来自哪个文件」的引用。原因是：多轮对话每次都要把整段历史  
重发给模型 —— 历史里的图片只剩引用的话，**第二轮开始模型就看不到它了**，  
用户问「这张图里的报错什么意思」会得到一脸茫然。

代价要说清楚：文件内容会被复制进这份本地数据库，截图（可能包含屏幕上的任何东西）  
也会随消息落盘。这是「把附件发进对话」这个动作本身的一部分，  
界面上有对应的说明，「重置本地数据」会一并清掉。

顺带两个细节：

- 只发附件不写字的消息也要进历史。按 `content` 过滤会把它整条丢掉
- 这种消息的会话标题从附件名来，否则会话列表里会出现一排分不清的「新会话」

### 「这个模型能看图吗」由用户声明，默认不能

我们没法从模型名可靠地判断这件事，所以做成设置项。**默认 false**，  
因为猜错的代价不对称：标成不支持但实际支持，用户多点一下开关；  
标成支持但实际不支持，就会把一张图发给文本模型，换来一个看不懂的 API 报错。

门禁在 Rust 侧（`stream_chat` 里检查），前端也拦一道并说清去哪里开。  
前端把发送按钮禁掉只是体验 —— 命令是可以被直接调用的。

### 发送前确认

带附件发送会先弹一次确认，列出**到底要发哪些内容**：文件名单个列出、各自多大、  
合计多少，并说明附件会保存在本地会话里。不带附件时不弹 —— 确认要出现在有风险的地方，  
到处都弹会让人养成闭眼按回车的习惯。

## 键鼠模拟与可控自动化任务（阶段 D 收尾）

**协议与安全边界单独写成了一篇文档：[`docs/AUTOMATION_PROTOCOL.md`](./docs/AUTOMATION_PROTOCOL.md)。**  
这一节的篇幅主要留给「为什么这么设计」。

### 这一项和前三项的性质不同

读文件、截屏、发附件都是**读** —— 最坏情况是「被看走了不该看的东西」。  
这一项是**写**：它会真的去动用户的鼠标和键盘，最坏情况是  
**「用户在自己没预期的地方点出了后果」** —— 发出去一条消息、删掉一个文件、点掉一个确认框。

所以前三项靠「授权范围 + 可见性」兜底，这一项必须靠**协议本身表达能力的上限**。

### 没有循环，是类型层面的

协议只有四种动作：`move` / `click` / `type` / `wait`。  
`AutomationAction` 是个扁平枚举，没有条件、没有变量、没有递归 ——  
**协议表达不出「重复执行」这件事**，所以不可能写出无限循环。

这比「运行时检测到死循环再拦住」可靠得多：后者要靠启发式判断，前者根本表达不出来。  
契约测试会去数枚举的变体，多一个都要先想清楚「它能不能被用来表达循环」。

### 最要紧的一条规则：`type` 必须跟在 `click` 后面

文字走的是键盘事件，它会打到**当前有焦点的窗口**上。  
如果允许凭空 `type`，那么执行时焦点在哪个窗口，完全取决于用户在确认和执行之间  
有没有切窗口 —— 而**这件事在预览里看不见，因为预览里根本没有「窗口」这个概念**。

所以协议要求每个 `type` 之前必须至少出现过一次 `click`：焦点必须是我们在同一个任务里  
点出来的，而不是碰运气碰上的。违反时的提示不是「格式错误」，而是把上面这段道理说清楚。

### 坐标从截图上来

面板里显示着刚抓的那张截图，**在图里点一下就把坐标填进对应的动作**，  
每个定位动作还会在图上标出带序号的点，方便对着图核对顺序。

这也是为什么这一项排在截屏后面做：没有截图，用户没有任何可靠办法知道某个位置  
在屏幕上的坐标是多少。

### 三层保护，缺一不可

|                   | 表达什么          | 落点                                      |
| ----------------- | ------------- | --------------------------------------- |
| **开关**（默认关）       | 「我同意这件事存在」    | `permission.input_simulation`，门在 Rust 侧 |
| **预览 + 确认**（每次都要） | 「我同意这一次做这些动作」 | 逐条列出动作的人话描述；**不做「记住这次选择」**              |
| **停止 + 报告**       | 出问题能叫停，事后能回看  | 中断标志 + 每步一条日志                           |

确认之后还有 **3 秒倒计时**才真的动手 —— 用户的手还在鼠标上，第一条「移动」会把光标拽走。  
弹窗里那句「请把手从鼠标上拿开」必须是真的，所以倒计时也得是真的。

### 校验发生在动手之前

`run_automation` 的顺序是：**先过门禁 → 再校验 → 最后才创建输入设备**。  
校验失败时鼠标一次都不该被移动过。校验的内容包括数量、总时长、坐标范围、  
文本长度，以及上面那条「输入之前必须有点击」。

前后端各做一遍同样的检查：前端做是为了让用户在点「执行」之前就看到问题，  
Rust 做是因为前端不是可信边界。两边写歪了会被契约测试发现。

### 日志里不记你输入的文字

执行报告里每一步都有，但 `type` 那一步**只记字数，不记内容**。  
理由：日志会落到磁盘上长期留着，而用户输入的文字可能包含任何东西 ——  
在界面上看一眼，和执行之后在文件里留一份，是两件事。

### 动作列表刻意不持久化

编辑中的动作列表只在内存里，切走标签页还在，关掉应用就没了。

这是有意的：一个存下来的动作列表会一直躺在那里，而你早就忘了它写了什么 ——  
可它执行起来是真的会动鼠标键盘。**忘记之后还在，是错的那一侧。**

## 让模型自己请求附件（阶段 E 第一步）

前面几步里，附件是**用户手动挑**的。这一步把方向反过来：模型可以说  
「我需要看 notes.md」，然后由用户决定给不给。

### 请求链路

```
模型：tool_call read_file({"path":"notes.md"})
  ↓ 停下来，不执行
界面：模型想读一下这些文件，允许吗？ [逐项允许 / 不允许]
  ↓ 用户点了
Rust：read_authorized_file(relative)  ← 四道防线照旧
  ↓
模型：tool 结果 + 继续回答
```

### 三个刻意的决定

**① 能力没开就不把工具给模型。** 截屏关着时，`take_screenshot` 根本不出现在请求里 ——  
模型连它存在都不知道。这比「先给它、执行时再拒」对用户友好：不会出现  
「模型一直在请求一个永远批不下来的东西」。

**② 每一次都要用户点头，不做「记住这次选择」。** 一次授权长期有效，等于把开关做废了。  
待批准的请求还会挡住新消息 —— 插进来的话，工具结果的 id 就对不上了。

**③ 拒绝也要告诉模型。** 不说清楚的话，它会一遍遍重试同一个请求，  
用户看到的是「模型卡住了」，而不是「我刚才拒绝了」。

### 模型给的路径是不可信输入

它可能是绝对路径、带 `..`、或者符号链接。所以前端**不做任何路径判断**，  
原样交给 `read_authorized_file` —— `file_access::resolve_within_root` 那四道防线  
才是真正的边界。前端自己也检查一遍，只会让人误以为那里也是边界。

有契约测试盯着这件事：`executeToolCalls` 里不许出现 `resolve(` / `normalize(` 这类调用。

### 截图走不过工具结果那条路

OpenAI 的 `tool` 消息只收文本。把 base64 塞进去，模型既看不到图，还白占一堆 token。

所以截图请求的结果是两件事：

1. 工具结果说「已抓取一张 2560×1440 的截图」；
2. 图片单独作为一条**带附件的消息**进去，模型才真的看得到。

### 轮数上限

一次对话最多 3 轮「模型要 → 用户批 → 再问」。没有上限的话，模型可以一直要东西，  
而**每一轮都要用户点一次确认** —— 用户最后会闭眼点「允许」，这个确认就白做了。  
到上限会明确告诉用户「已经停下」，而不是静默停住。

### 重放历史时不复刻协议形状

工具结果在**本次对话内**用标准的 `role:"tool"` 消息发回去（协议要求 id 对得上）。  
但**落库时不存工具消息**：消息表里存的是「助手说了什么」这个投影，  
没有 `tool_call_id` 这种东西。

所以读到的内容被挂在那条回答的 `attachments` 上 —— 下一轮重发历史时，  
它就是上下文（和用户手动附件的处理完全一样），界面上也说得清「这条回答参考了什么」。  
代价是重放时少了协议形状，模型读到的是同样的内容。

## 新增一种平台能力时，要同时补齐什么

阶段 C 起会陆续引入 Tauri 插件和新能力。每加一项，**六件事必须一起做**，  
只加前端按钮是不算的：

|   | 要做的                                         | 谁来保证                                           |
| - | ------------------------------------------- | ---------------------------------------------- |
| 1 | Rust / Tauri 配置（feature 或插件、模块、命令、**插件注册**） | `tests/contract/capability-checklist.test.mjs` |
| 2 | capabilities 权限（而且不能顺带多放开）                  | 同上                                             |
| 3 | `PlatformService` 接口 + 能力枚举                 | 同上                                             |
| 4 | 浏览器模式 fallback（明确抛错，不静默）                    | 同上                                             |
| 5 | 单元 / 契约测试                                   | 同上                                             |
| 6 | Windows 桌面构建验证（`tauri build --no-bundle`）   | 人工 / CI                                        |

用法：先在 `tests/contract/capability-checklist.test.mjs` 的清单里补一行，  
再照着自己列的 `desktopCommands` / `rustModules` / `rustPlugins` 去实现。  
漏了哪一步都会在 `npm run test:contract` 里红掉 —— 包括「实现完了但忘了改声明」，  
以&#x53CA;**「插件忘了 `.plugin(...)` 注册」**（那种情况编译通过、功能静默消失）。

## API Key 的旅程

这是整个工程最较真的地方，值得单独说清：

```text
用户在设置页输入 Key
   │
   ├── 浏览器模式 → 只放在内存。不写 localStorage、不进日志、刷新即清空。
   │
   └── 桌面模式  → invoke('save_model_config')
                      ├── apiUrl / modelName → SQLite 的 settings 表
                      └── apiKey            → Windows 凭据管理器（keyring）

发起对话时
   │
   桌面模式：invoke('stream_chat', { request })   ← 注意：参数里没有 Key
                 Rust 自己去凭据存储里取，装进 Authorization 头，发出去。
                 前端从头到尾没有搬运过凭据，也拿不到它。
```

三道结构性保证，都不靠「记得别写」：

1. **数据库里没有落点。** 迁移脚本中没有 `api_key` 列，`settings` 表里也没有  
   `api_key` 键（有测试扫迁移脚本的字面量）。
2. **类型里没有入口。** Rust 的 `PersistedModelConfig`、前端的 `AppSettings`  
   都不含 `api_key` 字段。想写进去得先改类型，改类型就过不了评审。
3. **命令签名里没有参数。** `stream_chat` 不接收 `api_key`，只接收  
   `ChatRequest`（模型 + 系统提示词 + 消息）。

再加一道保险：`src-tauri/src/redact.rs` 会把 `sk-...` 与 `Bearer ...` 抹成掩码，  
任何要展示的错误信息都先过它。前端同理，日志统一走 `src/lib/log.ts`。

## 为什么浏览器模式不接真模型

技术方案第 5 节写的是「浏览器 Demo 仅允许使用 mock 数据，不连接真实模型」，  
理由是 API Key 不能明文落在浏览器存储里。阶段 B 没有推翻这条，而是给了它一个  
更好的出口：**想让模型真的回答，就用桌面版**。

所以在 `src/services/model/index.ts` 里，浏览器分支保持返回离线实现是刻意的。  
有契约测试盯着这个分支不被顺手改掉。

## CSP：为什么主题脚本要单独放一个文件

桌面版的 WebView 设置了 CSP：

```text
script-src 'self'          ← 不允许内联脚本
connect-src ipc: http://ipc.localhost   ← 没有外网出口
```

`index.html` 里原本有一段内联的主题初始化脚本（避免首屏闪白）。为了它放开  
`'unsafe-inline'` 等于把整个应用的脚本策略降级，不划算。所以把它挪到了  
`public/theme-init.js`：同源外链脚本，`script-src 'self'` 就够了，  
并且仍然在 `<head>` 里同步执行。


开发模式另有一份 `devCsp`，只多放行 Vite 的 HMR 连接。

## 构建产物与代码分割

`npm run build` 现在产出 5 个 JS chunk，没有哪个超过 500 KB：

```text
vendor-react          219 KB   react / react-dom / scheduler
index                 151 KB   应用代码与共享依赖
vendor-ui              87 KB   Radix / sonner / lucide
SettingsPanel          52 KB   设置页表单（react-hook-form + zod + Switch）
rolldown-runtime      0.6 KB
```

两点说明，免得被数字误导：

1. **总体积没有变小**，只是被分开了。「首屏少解析」是真的省 ——  
   设置页那 52 KB 要等用户点开设置才加载。
2. **对桌面版来说，拆包省的不是流量。** Tauri 的资源是从本地磁盘通过自定义协议读的，  
   没有网络往返。这里真正有价值的是**启动时的解析与编译开销**，  
   以及「谁的体积」在构建报告里能一眼看清。

拆包规则在 `vite.config.ts`，只固定「react」和「UI 库」两个组，**不设兜底组**：  
兜底组看着整齐，实际会把「只有设置页才用的库」也钉进首屏，正好抵消按需加载的收益。  
谁被谁用到，交给打包器按实际引用关系判断。

有契约测试盯住这两件事不被改回去（`前端做了代码分割，且设置页是按需加载的`）。

## 相对方案做的几个判断

1. **模型地址与模型名持久化，API Key 不持久化。**  
   产品设计 3.2 要求「保存本地配置」，技术方案只禁止 Key 落盘。
2. **阶段 A 的存储用 Web Storage，不在浏览器里跑 SQLite WASM。**  
   `StorageService` 的接口按 SQL 操作命名，数据按三张表分开摆，阶段 B 照搬即可。
3. **Rust 侧引入了四个 Tauri 插件**（日志、通知、开机自启、全局快捷键），但  
   `capabilities` 里**至今仍然只有 `core:default`**。

   这一点值得单独说明，因为它和「引入插件就要放开权限」的直觉相反：  
   插件全部只在 Rust 侧使用，前端拿到的是自己的窄命令。  
   我们一开始也以为阶段 C 会往 capabilities 里加东西，**实际做下来四个能力都不需要** ——  
   只要坚持「前端只调自己的命令」就一项权限都不用开。  
   （真正会需要放开权限的是**前端直接调插件 JS API** 那种写法 —— 本项目没有采用。）

   托盘用的是核心的 `tray-icon` feature，同样不是插件。  
   有契约测试同时比对权限清单、依赖清单、插件注册，  
   并单独断言「前端不依赖任何 Tauri 插件的 JS 包」。
4. **设置页的文案全部来自服务层自述**，没有一句写死的。  
   同一个界面要如实描述两种运行环境，硬编码文案必然在其中一种里撒谎。

桌面端的行为（托盘、通知、自启、快捷键、系统对话框）自动化测不了，
有一份逐项清单：[`docs/DESKTOP_ACCEPTANCE.md`](./docs/DESKTOP_ACCEPTANCE.md)。

## 下一步（阶段 E 之后）

阶段 E 的第一步（工具调用 + 用户确认）做完了。往下比较自然的方向：

1. **多轮工具调用的体验打磨。** 现在模型一次请求里的多个调用会一起列出来，  
   批准之后一次性执行；但执行过程中的进度、以及「这一步失败之后模型怎么继续」  
   还没怎么设计。这是最值得先做的 —— 它决定这个功能是「能用」还是「好用」。
2. **多屏支持。** 截屏、自动化、工具调用的截图都只认主屏，坐标空间也是一套。  
   多屏要处理负坐标和坐标系原点，拼接结果和用户直觉未必一致 ——  
   真有人需要时再做。
3. **历史与上下文管理。** 现在 `MAX_HISTORY_TURNS` 是硬截断，附件内容又比较占地方。  
   摘要压缩是技术方案里提过但还没做的一块。

## 已知缺口

- **关窗口缩到托盘在真实桌面会话里失效了**（2026-10-18 验收发现）。
  点 × 之后进程直接退出，日志里**没有**「收到关闭请求」这一行 ——
  说明 `on_window_event` 里那段关闭判定压根没被调用，而不是判定成了「退出」。
  2026-10-15 和 10-16 的日志里还出现过「窗口已隐藏到托盘」，所以是这之后引入的回归。
  详见 `docs/DESKTOP_ACCEPTANCE.md` 的验收记录。

- **工具调用没有流式进度。** 工具请求要等整段参数收完才交给界面（半截 JSON 推上去只会显示乱码），  
  所以模型「正在要东西」的那几秒里，界面只有一个光标。多轮调用的进度提示还没做。
- **重放历史时不复刻工具调用的协议形状。** 读到的内容挂在助手那条消息的附件上，  
  模型读到的是同样的内容，但少了 `tool_call_id` 那层结构。要做「严格复刻」得给消息表  
  加两列并让 `role` 支持 `tool`，目前判断不值得。
- **一次对话最多 3 轮工具调用。** 到上限会停下并说明，不再自动继续。
- **自动化只支持主屏，也只认坐标。** 没有「对某某窗口操作」这种表达 ——  
  加窗口枚举与标题匹配是一整套会出错的判断逻辑，而坐标至少是用户自己选的。  
  代价是：点下去会发生什么，取决于坐标底下是什么，我们不做任何保证。
- **自动化任务的每一步之间没有「看结果再决定」的能力。** 协议里没有条件分支，  
  所以它做不了「如果弹窗出现了就点确定」。这是刻意的取舍：  
  有分支就意味着能表达循环，而这一项的风险主要来自「用户没预期到哪里会失控」。
- **按下 / 抬起是分开的。** 只支持完整点击，不支持拖拽和长按。
- **文件与截图目前只在设置页手动预览，不进入模型上下文。** 权限、抓取和预览已接好，  
  但 `ChatRequest` 仍然只有文本消息；需要单独设计附件展示、逐次发送确认，以及模型不支持图片时的提示。
- **截屏只抓主屏。** 多屏环境下会如实告诉用户「检测到 N 块屏幕，这里只截了主屏」，  
  而不是默默只给一块。多屏拼接需要自己贴图，而且拼接结果和用户的直觉未必一致，  
  留到真有需求时再做。
- **桌面模式没有自动化 UI 测试。** 跑 Tauri 窗口需要真实 GUI 会话，脚本无法无头执行。  
  窗口内行为的等价覆盖靠 Rust 单元测试（144 项）+ 环境切换与能力探测单元测试
  - 桌面外壳契约测试。但「托盘图标真的出现了吗、双击真的能恢复窗口吗」  
    「系统通知真的弹出来了吗」这类事只能人工验证一次。
- **托盘、系统通知、开机自启、全局快捷键都没有在 CI 上验证过。** `tauri build --no-bundle` 只证明它能编译链接，  
  不证明它在真实桌面会话里行为正确。
- **Windows 通知依赖应用的 AppUserModelID。** 插件用的是 `tauri.conf.json` 里的  
  `identifier`。未安装、直接双击运行的 exe 可能出现「通知不显示」或  
  显示成未知来源 —— 这是 Windows 通知机制的限制，不是代码问题。  
  正式分发时装成 NSIS 包（`npm run build:desktop`）通常就正常了。
- **文件读取只认 UTF-8。** 没有做编码探测：GBK 编码的旧 .txt 会被判为  
  「不是 UTF-8 文本」并明确告知，而不是塞一堆乱码给模型。  
  加编码探测需要引入 `encoding_rs` 并做启发式判断，而误判会让内容静默变形 ——  
  在「说清读不了」和「可能读错」之间先选了前者。
- **符号链接的端到端用例在本机跑不了。** 这台机器上 `std::fs::symlink_file`  
  会返回成功，但产物根本不是重分析点（`read_link` 报「不是一个重分析点」，关掉沙箱也一样）。  
  用例因此在确认「真的建出了链接」之后才执行，否则明确打印【跳过】。  
  判定逻辑本身改由注入探测函数的方式覆盖（`symlink_check_*` 那几条），  
  所以「有没有逐段检查、最后一段查不查」是被测到的；  
  **但「真实链接会被拒绝」这一条需要在能创建符号链接的机器上人工复验一次。**
