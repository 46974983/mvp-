# 自动化动作协议与安全边界

> 状态：随阶段 D「键鼠模拟和可控自动化任务」一起定的第一版。
> 这是**先于实现**写下来的东西 —— 协议一改，前后端和 Rust 三边都要跟着动，
> 所以它值得单独成文，而不是散在代码注释里。

## 为什么这一项要单独定协议

前三项能力（读文件、截屏、把附件发进对话）都是**读**：读文件、读屏幕、
把读到的东西发给模型。最坏情况是「被看走了不该看的东西」。

键鼠模拟是**写**：它会真的去动用户的鼠标和键盘。最坏情况不是「信息泄露」，
而是**用户在自己没预期的地方点出了后果** —— 发出去一条消息、删掉一个文件、
点掉一个确认框。这两类风险的性质不同，所以处理方式也不同：
读那三项靠「授权范围 + 可见性」，这一项必须靠**协议本身表达能力的上限**。

## 一、动作协议

一个自动化任务就是**一个扁平的、有穷的动作列表**。没有别的。

```jsonc
[
  { "kind": "move",  "x": 640, "y": 360 },
  { "kind": "click", "x": 640, "y": 360, "button": "left" },
  { "kind": "wait",  "ms": 300 },
  { "kind": "type",  "text": "hello" }
]
```

| 动作 | 字段 | 说明 |
| --- | --- | --- |
| `move` | `x` `y` | 把鼠标移到主屏坐标（像素，左上角为原点） |
| `click` | `x` `y` `button` | 移到该点并点击。`button` 是 `left` / `right` / `middle` |
| `type` | `text` | 输入一段文字，走键盘事件（支持中文） |
| `wait` | `ms` | 等待若干毫秒 |

**协议里没有的东西**（这是刻意的，不是还没做）：

- ❌ 条件判断、分支
- ❌ 循环、重复、递归
- ❌ 变量、表达式、任何形式的脚本
- ❌ 按键组合（`Ctrl+C` 这类快捷键）
- ❌ 滚动、拖拽、多键连按
- ❌ 读取屏幕内容来决定下一步

**没有循环这一条是核心。** 协议在类型上就表达不出「重复执行」，
所以**不可能写出无限循环** —— 这比「运行时检测到死循环再拦住」可靠得多：
后者要靠启发式判断，前者根本表达不出来。

## 二、安全边界：几个上限，各自为什么是这个数

| 上限 | 值 | 为什么 |
| --- | --- | --- |
| 单个任务的动作数 | 20 | 预览要能一眼看完。超过 20 步的列表，用户点「确认」时其实没在看 |
| 单个 `wait` | 10 秒 | 再长的等待没有意义，而且会把「取消」的响应时间拖到不可接受 |
| 整个任务的总时长 | 60 秒 | 兜底。超过就中止并说明，而不是让它在后台跑下去 |
| `type` 的文本长度 | 2000 字 | 一次粘贴几千字本来就不是「模拟操作」的合理用法 |
| `type` 动作的个数 | 5 | 同上的理由：输入堆多了不像是有界操作 |
| 坐标 | 必须落在主屏内 | 只截主屏（见 README 截屏一节），坐标用同一套坐标系 |

### `type` 必须跟在 `click` 后面

这是整个协议里**最要紧的一条规则**。

文字走的是键盘事件，它会打到**当前有焦点的窗口**上。如果协议允许凭空 `type`，
那么执行时焦点在哪个窗口，完全取决于用户在确认和执行之间有没有切窗口 ——
**用户在预览里看不到这件事，因为预览里根本没有窗口这个概念。**

所以协议要求：**每个 `type` 之前必须至少出现过一个 `click`。**
焦点必须是我们在同一个任务里点出来的，而不是碰运气碰上的。

违反时给的不是「格式错误」，而是：

> 这段文字会打到当前有焦点的窗口。协议要求先点一下目标位置，把焦点点出来，
> 再输入文字 —— 否则你可能在预览里看不到它会被打进哪里。

### 坐标从哪来

从**截图**上来。设置页有一张刚抓的截图，在图里点一下就把坐标填进对应的动作。
截图的像素坐标和屏幕坐标是同一套，不需要换算。

（这也是为什么这一项排在截屏后面做：没有截图，用户没有任何可靠办法
知道某个位置在屏幕上的坐标是多少。）

## 三、门禁：四件事，和截屏同一套

模式写在 `src-tauri/src/permissions.rs`，这一项是第二个使用者。

1. **默认关闭。** `DEFAULT_HIGH_RISK_ENABLED = false`，
   数据库里读这一项时只认明确的 `"true"`，值坏了就回到「关」。
2. **门开在 Rust 侧。** 前端禁按钮只是体验 ——
   命令是可以被直接调用的，所以判断必须在 `run_automation` 的第一行。
3. **失败说人话。** 拒绝时说清是哪个能力、为什么不行、去哪里开。
4. **每次执行都留痕。** 每一步一条日志，界面上能回看「刚才它做了什么」。

### 前端碰不到任何系统 API

`PLATFORM_CAPABILITIES` 里没有「输入模拟」这一项的实现细节，
前端能调到的只有窄命令：

```
run_automation(actions)   ← 收的是一个动作列表，不是「执行任意操作」
stop_automation()         ← 中断当前任务
automation_last_run()     ← 最近一次的执行报告
```

**没有「按某个键」「滚一下」这种命令。** 想加新动作，必须同时改协议、
改校验、加上限、加预览文案 —— 这是故意的摩擦。

## 四、确认：每次执行前都要看一遍

执行分成两步：

1. **预览**：把动作列表翻成人话（「移动到 (640, 360)」「点击左键」…），
   连同坐标的来路一起摆出来；
2. **确认**：用户点了才执行。

确认弹窗里必须包含**「开始后 3 秒内把鼠标挪开」**这句提示 ——
任务一开始就会真的动鼠标，用户需要一点时间把手拿开。

预览和确认不做成「记住这次选择」：**每一次执行都要重新确认。**
自动化任务不是「一次授权、长期有效」的东西。

## 五、停止与超时

- **停止**：执行循环的每一步之间检查一个取消标志。用户点「停止」
  或者窗口关闭都会置位，最多延迟到当前这一步结束。
  `wait` 的等待被切成小片，所以长等待也能及时中断。
- **超时**：累计耗时超过 60 秒就中止，并在报告里说明是超时中止的。
- **失败**：某一步失败（比如坐标超出屏幕）就停下，不继续后面的动作 ——
  后面那些动作的坐标很可能基于「前一步成功了」这个假设。

三者都会体现在返回的执行报告里：`stopped` 字段区分「正常跑完」和「被中断」。

## 六、操作日志

执行报告里每一步都记：序号、动作的人话描述、成功与否、说明、时间。

**只记动作和结果，不记屏幕内容。** 日志里的坐标是用户自己填的，
而屏幕内容属于「读」那一类，有它自己的可见性规则。

## 七、刻意接受的限制

- **只支持主屏。** 多屏下坐标空间会更复杂（负坐标、坐标系原点），
  而截屏也只截主屏 —— 两者保持一致比各自为政好。
- **不能选择窗口。** 没有「对某某窗口操作」这种表达。协议只知道坐标，
  不知道坐标底下是谁 —— 加窗口选择等于加一整套窗口枚举与匹配逻辑，
  而且「窗口标题匹配」本身就是个会出错的判断。
- **不保证点击生效。** 我们只负责把事件发出去，不负责目标程序有没有响应。
  这也是为什么每一步都要有 `wait` 的空间。
- **没有回放/录制。** 录制会记录用户的真实操作，包括可能包含敏感信息的输入 ——
  那是另一类能力，需要单独的开关和说明。
